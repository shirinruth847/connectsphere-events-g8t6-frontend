## Reassignment notification reliability

The Lead's existing reassignment form changes only to protect the organiser's
AC4/AC10 notice. It stores an unconfirmed command before sending it and offers
Retry previous reassignment after uncertainty or reload. Its session-storage
key includes the trusted application user and event. Another reassignment is
disabled until the result is confirmed or definitively rejected. Explicit
logout clears recovery data through the existing session helper.

Storage cleanup compares the completed command's key with the current stored
key before removal. Request callbacks are invalidated when their view unmounts;
older successes, errors and completion callbacks cannot update a replacement
view or erase its recovery state. Pending fetches are allowed to finish because
their database action may already have committed; recovery retains the key.

Requires backend migration `20261028010000_spm192_reassignment_replay` before
deploying the matching backend and frontend. First assignment is unchanged.
Outcome/rejection/cancellation workflows and database grant cleanup belong to
their own tickets; this correction does not add those capabilities.

Local checks, 28 October 2026: Node 147/147, Vitest 3/3, lint with zero errors
and one existing unused-variable warning. The full mocked browser suite passed
343 journeys; after the final malformed-response guard, a fresh production
build/type check and all 14 SPM-192/Lead assignment journeys passed. Recovery

do not establish hosted backend/database integration.

and the existing unused `historyIcon` warning. `git diff --check` passed. This

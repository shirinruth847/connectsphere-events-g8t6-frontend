# SPM-199 — Organiser Views Own Event

Ticket: https://yvery.atlassian.net/browse/SPM-199

Companion branches in both repositories:
`feature/SPM-199-organiser-event-arrangements`.
Integrated frontend main `f845de5` through local merge `16107a4`; backend main
`a31ad8a` and Master v1.4 are the companion baseline.

The existing organiser event page now loads three arrangement sections from
GET `/api/events/:id/arrangements` using the shared authenticated API client:
venue bookings and holds, equipment/technical arrangements, and safety
reviews. The dashboard shell, navigation and draft-editing flow are retained.
Existing owner and permitted organisation-member views use the same safe
response. A draft does not request arrangement data.

## Acceptance coverage

`tests/e2e/spm-199.spec.mjs` covers the agreed ten cases: owned event details,
status and coordinator, all venue bookings and primary, hold status/expiry,
venue unavailability and next action, technical requirements vs decisions,
safety comments and outcomes, internal-field rendering exclusion, access
denial and empty states. Additional journeys cover a provider failure and
keyboard retry, session expiry, draft regression and desktop/mobile layout.
Real API authorization and response secrecy are verified by the backend
route/model suites; browser mocks alone do not prove those properties.

The TC05 operational-unavailability regression verifies that affected bookings
keep their approval status, active holds show the pending-coordinator action,
unaffected/historical arrangements gain no current warning, and recorded
replacement history remains visible after refresh. The backend's model tests
establish detection from PostgreSQL INACTIVE/UNDER_MAINTENANCE/unusable venue
states, including absent incident storage and MongoDB failures. Existing UI
components consume the same safe impact contract; no frontend runtime change
is needed for this fix.

Refresh arrangements drops stale section data while reloading. An active
hold schedules a refresh at expiry. The frontend uses the backend organiser
event label and never changes it based on a resource approval. Safety reviews
for earlier arrangements are labelled as previous rather than current. The backend
rechecks the event version/state after reading the sections and returns
`409 ARRANGEMENTS_CHANGED` if they changed during loading. The frontend clears
all previous sections, explains the conflict, and offers an explicit refresh.
A regression journey verifies that an old approval disappears until a new
response succeeds. The event overview can be updated with a page reload.

The organiser now uses main's `SafetyRoundCard` through an explicit
organiser-safe adapter. It mounts one safety section and performs one aggregate
arrangements request; the existing standalone safety API/component remains
available to the other role views. The main organiser-outcome journey was
updated to exercise the aggregate response while retaining its privacy checks.
